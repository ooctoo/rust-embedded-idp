## 2 契约落点

### 2.1 列表与定位

- 列表仅使用真实类型、PKCE与登记时间排序条件；无名称搜索。查询和重置通过新列表实例清空旧游标；排序条件提交后回第一页。保留服务端顺序，不在前端排序或计算全量条数。
- 页码仅表示游标栈位置，上一页/下一页遵循 `has_more/next_cursor`，无总数、最后一页或随机跳页。读取失败保留筛选，刷新/重读沿用原回第一页行为。
- 加载、成功、未筛选空、筛选无匹配、403及其他读取错误分别显示；失败不显示为零条数据。普通401、sessionChanged等继续由原client和UI-B处理。
- “按ID登记/编辑”先输入稳定ID，再读取配置。已有ID进入编辑；详情404后还须成功读取客户端列表，确认当前客户端模块可读，才进入既有登记分支。403、5xx、畸形响应或模块整体不可用均不转为登记。
- 精确 `.` / `..` 属于原ID语法，但现有HTTP详情路径会被浏览器归一化，且原列表没有精确ID过滤。UI在发出该详情请求前明确提示当前入口无法安全读取，不把它误认为新对象；不改领域ID规则、不扫描全库、不新增后端端点。该兼容边界未被宣称为已完整解决。

### 2.2 配置、确认与反馈

- 字段保持原协议：名称最多256字节；最多32个回调、每个2048字节；ID最多128位既有字符；整个JSON最多16 KiB。公开桌面客户端强制PKCE，回调类型规则仍由既有服务验证；机密Web客户端保留原PKCE选择。
- 机密密钥不回显；已有密钥留空保留，新值显式设置/替换，转公开明确清除已有密钥。密钥仅在原Form内短暂保留；取消确认、关闭、重读与保存结束时清理，不进入差异摘要、URL、持久存储、运行截图或诊断。
- 确认区展示稳定ID、名称/类型/PKCE变化、原回调与最终完整回调、密钥处理方式和部署影响。明确upsert可能覆盖、回调完整替换、没有版本冲突检测、不自动撤销已有会话。没有增加CAS或幂等字段。
- 敏感值不保存在确认草稿中。返回修改后若仍需设置/替换密钥，应重新输入；新机密配置仍须满足原必填规则。
- 成功响应经过原client解析及字段核对后，持续结果显示对象、变化和作用范围；后续GET失败保留“已保存，重新读取失败”，不当成写入失败。
- 发送前的本地校验失败明确未发送请求，不标为写入未知。已发操作的明确4xx拒绝与5xx/网络/响应校验未知分开呈现；后两者均先阻止重复保存，须重新读取原ID并核对后再操作，无自动重试。
- 回读成功只能显示当前可见配置，不能证明未知请求的归因或具体Secret新值。未知提示保留到后续明确操作，密钥需要接入方核对；不补结果查询或跨对象动作台账。
- 重新读取或关闭有草稿/未知结果的侧板须明确确认，取消保留草稿。处理中禁止关闭；跨页/切目标继续走UI-B完整写操作活动计数与原会话revision，不更换管理认证。

### 2.3 响应式与可访问性

客户端筛选在窄屏纵排，表格只在自身横滚；侧板不超视口，内容可滚动。长确认区有名称和键盘焦点、限制高度且独立滚动，操作区保留在视口内。确认每次打开聚焦“返回修改”；返回编辑、错误后重读、关闭后触发器分别恢复焦点。

原说明文字实测为 `rgba(0,0,0,.45)`，本轮仅在UI-C范围改为设计色 `#58677c`；列表说明、字段约束与当前配置标签三处在白底实测均为 **5.76:1**。不将该抽样当作完整WCAG、屏幕阅读器或200%缩放验收。

- 对旧dot-only详情路径增加UI安全拒绝，防止已有配置被当作未登记；没有借机修改公共API。

- 并行浏览器复跑时出现过UI-B会话校验等待超时，最终串行复验通过；不改UI-B产品逻辑，不将失败尝试计为通过。

## 7 2026-10-21 客户端离页与会话失效专项补验

### 7.1 审查项与改动

上一轮只读审查确认实现仍复用UI-B守卫和原session revision，但原17组只直接验证侧板内部恢复，UI-B的角色页面回归不能代替客户端组件的跨页与会话时序证据。本轮在原脚本后增加UC18–27，不修改产品代码、公共API、会话协调器、宿主装配、依赖或UI-A/UI-B历史稿。

每个mode分别建立真实的工作台/客户端历史链，对草稿、确认层和未知写入执行取消Back、Forward、地址hash和菜单离开；Enabled的地址变化还尝试进入`tenant-a`成员页。取消后URL回到客户端页，原对象与状态保留；明确允许菜单离开后原弹层清除，返回重新定位必须读取服务端配置，不能带回未提交草稿或自动重放写入。所有被观察的客户端请求仍不带tenant/business头。

延迟读写先取得真实服务端响应，再由浏览器路由暂存。POST另外通过原ID独立GET核对已写入的名称。第二标签复用原浏览器上下文恢复Cookie，并实际调用`auth/session`核对tenant/account/session/client完整身份一致；原标签此时仍有工作区。只有第二标签真实logout返回204后，才要求原标签因原Coordinator的sessionChanged卸载工作区、确认层及Secret输入。之后释放暂存响应，等待响应体完成和浏览器绘制，再确认没有旧界面/成功提示恢复、没有额外POST。

处理中还检查hash和菜单离开均被alert阻断、确认按钮保持loading、返回按钮禁用、关闭按钮不存在且Esc不关闭；程序化再次激活保存按钮也不能产生第二次POST。旧参考行为与宿主直接嵌入能力沿原接口和产物回归，不增加另一套身份机制。

### 7.2 证据与限制

新增10组在Enabled、Disabled各执行5组，和原17组一起形成27组机器记录，见[results.json](design/ui-c/results.json)。UI-B共用守卫回归保留独立19组记录；本轮客户端专项不再只由角色页面的结果代替。
