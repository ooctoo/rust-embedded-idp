## 1 设计结论

建议把独立应用组织为**平台管理与租户管理两类工作区**，采用稳定侧栏、紧凑顶栏、明确管理目标、列表—详情—变更确认的后台结构。第一批改造复用现有 Ant Design、ManagementClient、BrowserSessionCoordinator 和真实管理 API。

“像 Ant Design Pro / shadcn 的后台”应首先落在导航、信息层级和操作流程。当前已有 Ant Design 5、React 19 适配补丁、真实列表、抽屉和确认弹窗；本提案建议先保留它们。引入整个模板或换组件库不是形成后台体验的前提。

社区对齐分三层：已有能力做完整管理体验；已有领域能力补使用闭环与证据；确实缺少的能力单独设计。MFA、账号恢复、联合身份、邀请、服务身份、事件投递等不能靠增加菜单变成已支持能力，也不作为本次 M1-02 的新增退出门槛。

可行性结论：**首批管理后台改造可在现有前端和管理 API 上完成；社区能力补齐需逐项进入独立契约设计。** 当前未发现必须先修改 Core、存储、配置装配或启动 M1-03–06 才能完成后台壳层的依赖。这里的“单体应用”指现有参考宿主的管理体验，不把 `embedded-idp-app` 升格为已验收的生产宿主。

## 2 现状与设计依据

### 2.1 已有实现

| `clients/accounts/tenants/members/roles/permissions/permission-directory/devices/sessions/audit/diagnostic.tsx` | 已有真实数据和写操作、抽屉、危险操作确认、错误恢复 | 做页面归类与交互统一，避免重写领域操作 |

当前属于“已有组件与业务页面，但工作台组织不足”。本轮 UI 判断来自源码、既有界面记录；没有把旧截图当作当前浏览器复验，也没有给未经测量的可访问性评分。

表中的页面导航目前由 Tab 和局部状态实现。侧栏、hash 路由、页面级 404、帮助入口与工作台均为拟新增的前端体验；统计聚合接口也不是现有能力。

## 3 产品对象与作用域

| 概念 | 含义 / 权威来源 | 界面规则 |
| --- | --- | --- |
| 全局账号 | 全局 ID 与凭证；跨租户共享账号身份 | 账号安全是平台级/单域管理；禁用或改密码提示全局影响 |
| tenant | 成员和授权边界；Enabled 的 0 为平台域 | 平台可选择管理目标；租户管理员不能靠 UI 改成平台身份 |
| client | 部署级客户端配置；DB/API 权威 | 客户端列在平台/单域“接入管理”，不能标为租户私有 |
| login_entry | 可信宿主配置中的稳定入口绑定 | 配置管理属于运行资料；后台不提供不存在的在线入口 CRUD |
| business_id | 租户内业务权限命名空间 | 仅权限/角色/分配/诊断等页面需要；不能从 client 或入口自动推导 |
| 管理会话 | 已认证主体、purpose、session tenant | 始终保留当前身份可见；与“正在管理的租户”分开 |
| 管理目标 | 平台管理员本次操作的目标租户 | 切换只是目标选择，不能伪造登录、签发新 session 或清除其他会话 |

Enabled 平台会话 Fixed0 选择目标租户，不调用 Choose 登录切换。Choose 入口的真实切租户保留原选择票据流程，成功后仍不自动注销有效源会话。Disabled 使用单域0，文案为“系统管理”，不展示无意义租户切换，也不照搬 Enabled 的平台域权限判断。

账号、租户、客户端是否属于某个自有产品，属于需求方配置选择。本库不强制“一产品一租户”；UI 继续使用通用“租户”，实例名称可展示产品名，不改存储语义。

## 4 信息架构与导航契约

### 4.1 工作区菜单

| 工作区 | 分组 / 页面 | 数据与动作 |
| --- | --- | --- |
| 平台 | 工作台 | 当前身份、可用任务入口、已有审计的最近一页；不造统计数字 |
| 平台 | 身份管理：账号安全、系统管理员 | 原账号状态/密码管理、保护管理员任命流程 |
| 平台 | 租户：租户列表、租户详情 | 创建、状态、注册策略、进入该租户管理目标 |
| 平台 | 接入管理：客户端 | 原 list/get/upsert；无删除/停用按钮 |
| 平台 | 安全与审计：平台权限、平台审计 | 内置权限只读/原有保护规则，审计查询与详情 |
| 目标租户 | 成员与授权：成员（含租户管理员授权）、角色、权限目录、权限诊断 | 保留 tenant/business/resource 范围、保护角色与版本规则 |
| 目标租户 | 安全：设备、会话、租户审计 | 原状态变更、绑定解除、撤销与审计；不把 IDP 设备当产品资产台账 |
| 单域 | 工作台、账号安全、客户端、成员与授权（含系统管理员授权）、安全与审计 | 按现有 Disabled 可用操作组合，不额外要求平台会话 |
| 全局辅助 | 当前会话、帮助 | 会话详情、已有接入文档；不显示 Secret 或原始 token |

“审计查看人员”是工作职责，不默认新增一个现有系统没有的只读角色。首批沿用当前权限模型；细粒度后台菜单/操作授权如需扩大角色矩阵，属于后续服务契约，不能在前端硬编码新角色即可生效。

现有 `Capabilities` 只有 tenancy 与登录策略，不是 `allowed_actions` 权限矩阵；验证会话也不等于取得所有管理权限。首批可据模式/会话域排除不适用菜单，但不据此承诺每个按钮已获授权；实际查询或操作被拒绝时呈现局部403。工作台最近审计区域可在首次读取403后隐藏/标明不可用，不循环探测或伪造“没有事件”。若以后要求按动作精准菜单授权，先设计服务端契约。

工作台不从多个分页接口逐页遍历来制造总数、活跃率、趋势或“系统健康 100%”。无服务端聚合时显示任务快捷入口及明确范围的最近记录；已知模式不适用或已获拒绝结果时不再请求该区域。`/readyz` 也不作为登录、全部入口可用或安全合规的总状态。

### 4.2 页面地址与刷新

拟定导航示例：`<ui-base>/#/platform/clients`、`#/tenants/<id>/members`、`#/tenants/<id>/roles`、`#/system/sessions`。这些是前端位置，不是新增 HTTP API。默认首页按真实管理会话选择工作区；不能仅凭 URL 选择权限。

- hash 只放非敏感页面定位。tenant、client、role ID 使用统一编码/解码和格式检查；未知页面展示局部 404，不发任意 API 路径。
- 角色详情/权限编辑需要 `(tenant_id, business_id, role_id)` 完整定位；不能仅以 role ID 或当前列表筛选补猜业务范围。首批可继续用页内抽屉，不强制所有详情都有 URL。路由仅映射固定页面标识到现有 client 方法。
- 邮箱查询、密码、Secret、token、selection ticket 不进 URL、埋点或 localStorage。首批筛选留在页面内存；可分享“页面 + 非敏感 ID”，不默认分享个人信息筛选。
- 前进/后退、复制链接和刷新后先恢复/验证管理会话，再读取目标与详情；权限不足为403状态，不回退匿名数据或猜另一个租户。
- 目标变化清空游标、已选择行、详情/写入草稿、旧请求结果。请求完成时核对 session/target 仍一致；不能把迟到的 A 租户响应显示到 B。
- 有未保存内容时提示放弃或继续编辑；写操作已提交且结果未知时提示先核对原目标，不切换目标后自动重试。
- API 地址仍来自唯一 `idp-api-base`，browser 描述仍来自唯一 meta。hash 不参与 API prefix、Cookie Path 或协调键计算。

保留当前 `app.tsx` 按 session/tenant 变更重挂工作区、`roles.tsx` 按目标变更重挂内容的效果。新壳层的内容身份须覆盖会话、管理目标、页面和必要业务上下文；浏览器回退、地址编辑与菜单点击走同一离页检查。提交中的写操作不能因换页变成自动重发；结果未知时在当前会话内保留不含 Secret 的原目标/动作提示，核对后再由用户明确离开。会话失效清理凭证和敏感草稿，不将其恢复到下一位登录者。

### 4.3 导航与认证恢复状态

`读取登录能力 → 恢复/登录 →（Choose 时选租户）→ 验证会话 → 装配可用工作区 → 读取目标页面`。

普通管理资源请求的401按现有 client 清除认证并清理页面；403保留仍有效的会话，展示当前目标无权限；普通读取网络失败可保留目标并重试。**restore/refresh/login/logout 不是普通读取**：其凭证清理、Cookie 协调阻断、响应丢失及开发模式403均服从现有 client/Coordinator，不以“网络可重试”强行保留旧凭证或重放 refresh。真实 Choose 选择中按现有规则暂停管理请求；取消选择、成功切换各沿用原状态转移。

多标签会话变化沿用现有 Coordinator 和 sessionChanged，冻结旧页面写操作并提示刷新；不额外实现第二套自动刷新锁。页面可以保留无敏感信息的地址意图，完成合法恢复后再重新验证目标，不恢复旧权限判断。

## 6 关键业务流程详细设计

### 6.1 租户准备与成员授权

仅 Enabled 平台管理提供“租户列表 → 创建租户”，沿用现有创建接口和初始管理员结构；Disabled 不暴露该流程。表单明确 tenant ID 不可随意更名、名称、注册开关以及已有账号/新账号两种管理员来源。新建租户表单建议显式关闭注册；这是后续 UI 候选默认，不改变旧 Disabled 初始化、旧参考注册默认或服务端默认。

提交前展示目标与管理员身份，密码只留当前表单内存，提交/关闭后清理。成功进入新租户详情，可继续成员/角色配置；超时按 tenant ID 重新读取确认，不自动重新创建、不宣称跨 API 总事务。租户不存在、停用、无权管理分别展示，不能将停用域恢复为active来方便进入。

当前租户创建的账号（选择新账号时）、租户、初始成员/保护角色授权和审计由后端事务承接；代码及已有原子性测试已静态核实，无需为此新增事务服务。之后的额外成员、业务权限和角色配置是独立操作，不能写成“整个接入向导失败全部回滚”。回读到租户只能确认可见状态，不能自动证明响应未知的每个后续步骤成功。

成员页区分“关联已有账号”“创建账号并建立初始成员关系”“停用/移除该租户成员”；动作按模式和真实身份提供：关联已有账号仅给 Enabled 平台管理身份；创建账号给平台/Disabled 域0的有权管理员；Enabled 非0租户会话不能因进入成员页获得前两项权限。成员状态操作仍按原接口权限和状态规则，Disabled 不展示 Enabled 成员移除流程。账号全局禁用另走账号安全页面，不能让租户管理员以局部成员管理权限执行。菜单显隐只是交互，所有动作继续由服务端授权。

角色分配必须展示 tenant、business、role 与绑定范围：普通业务角色为 resource type 的 `type/instance`，`business_admin` 为 `business` 范围，覆盖该业务当前及未来全部有效权限，不获得 IDP 管理权限。不能将业务管理员转成显式权限快照，也不能让受保护的系统/租户管理员走普通角色编辑。具体资源 ID 的真实归属由产品后端保证；权限诊断是带审计的时点判断，展示现有 allow/deny 与 audit ID，不代表资源存在，也不是后续请求的授权凭证。

### 6.2 客户端与应用接入

菜单首期仍命名“客户端”，详情包含名称、稳定 ID、原 public_desktop/confidential_web 类型、PKCE、完整回调集合、密钥配置状态。可用友好显示文案解释公开客户端，但不改变协议 enum，也不暗示任意 HTTPS 回调被当前 PublicDesktop 校验接受。

“登记客户端”先输入 ID 并查询：存在则明确进入编辑，不将 upsert 伪装为 create-only。编辑保存显示差异、整套部署影响和回调完整替换。当前接口没有 CAS，重新读取只能帮助核对，不能声称消除了并发覆盖；若要防丢失更新，需要后端版本契约，另行安排。

机密客户端密钥不回显；留空保留已有密钥，显式新值表示替换，确认界面仅显示“保留/替换/不使用”。失败/响应未知后阻止盲重试，先重新读取可见状态；无法通过回读确认具体 Secret，应按已有密钥处理边界核对接入方，不显示 hash。

client、tenant、login_entry、business_id 没有数据库统一关联表。首期不展示推断出来的“关联产品数量”“已启用登录入口”或按钮式“发布配置”。详情帮助解释：登记 client 后，还需运行配置引用及受控重启；M1-02 新模式暂不支持业务集合运行。未来如增加“应用接入向导”，只能做已有对象的受控步骤与明确人工边界，不能偷偷引入配置热更新或 P3 控制器。

### 6.3 会话与设备处置

会话页沿用目标域筛选、主体/设备/client等现有字段；区别“撤销一个会话”和“撤销该主体在目标域内的会话”。确认框列出实际作用域；当前接口不提供跨全部租户总撤销时，不显示“全平台退出”。成功后的已撤销状态来自回读/返回，不能仅凭列表消失判定。

设备页完整呈现 pending/active/disabled/revoked，状态跳转仍严格采用原 API 规则，不能按状态列表生成任意转换按钮。会话也保留 pending/active/revoked/expired，不把 pending 计为已可用会话。保留绑定信息、必要原因和原状态并发校验。解绑人员会话、人员持钥证明、无人员设备传输证明分别表达，不提供“一键切为免证明”之类降级操作。设备的出厂/资产归属由宿主负责，UI 只展示现有 IDP 资料。

### 6.4 审计与问题定位

审计页分平台审计与目标租户审计，筛选只使用原 API 的 actor/business/operation/时间范围。默认时间排序、游标分页；详情显示时间、操作者域与ID、目标域、认证来源、request ID，以及事件实际返回的 change。仅对确有 before/after 的事件展示前后对照；创建、批量撤销等事件不保证完整快照，不推断或补造缺失值。时间带时区提示，长 ID 可复制并给状态反馈。

现有审计字段不等于具备完整登录风控日志、跨系统追踪、可靠 webhook 或审计仓库。首期不增加不存在的 IP/地理位置/风险评分。全量导出、保留期、外部订阅、结果未知按 request ID 服务端查询等若无对应 API，均登记后续能力，不能靠前端拉取全部分页模拟成熟平台。

### 6.5 通用状态与恢复

| 状态 | 界面行为 | 禁止的误导 |
| --- | --- | --- |
| 首次加载 | 局部 skeleton，保留标题与目标；请求晚到按作用域丢弃 | 把加载中的空数组显示成“无成员” |
| 无数据 / 筛选无匹配 | 分别提示首次准备或调整筛选；只提供有权限且已实现的动作 | 展示假示例为真实记录 |
| 读取失败 | 显示目标与重试入口，保留可用筛选 | 自动切到其他租户或统计为0 |
| 无权访问 | 403局部结果，保留返回可用页入口 | 将隐藏菜单视为后端授权 |
| 版本/状态冲突 | 保留非敏感草稿摘要，读取新状态后重新确认 | 无条件覆盖/自动重发写操作 |
| 写入结果未知 | 标明“未确认结果”，禁重复提交，先按对象回读核对 | 将超时直接标失败并自动重试 |
| 写入成功 | 明确对象/变化/范围；返回列表或继续相关工作 | 只有短暂 toast 且看不到结果 |
| 会话失效/跨标签变化 | 停止写入、清敏感状态、按原机制恢复或重新登录 | 复用旧凭证继续后台请求 |

### 6.6 账号安全与受保护管理员

账号状态/密码使用已有账号安全抽屉。密码变更会在所有域退役该账号的 session、refresh、authorization code 和未完成租户选择；确认页面面向用户说明“所有域的现有登录和待完成登录将失效”，不只写“更新当前租户密码”。自己改密/变更身份状态后沿用 client 清理并重新登录；启用账号不恢复已失效凭证，closed 账号仍只读。界面调整不能把现有管理员改密误称为用户自助恢复。

平台“系统管理员”和目标租户“成员 → 租户管理员授权”继续使用 `AdministratorDrawer` 的专用接口。任命资格由服务端提交时复查，任命不创建账号或成员关系；业务租户成员不自动具备平台成员资格。撤销仅撤管理授权，保留账号、成员及业务角色，后续请求按最新权限判断；不把“撤管理权”与“撤销全部会话”混为同一操作。

最后一位有效管理员、账号最后一个未移除的成员关系及受保护角色的原规则和并发冲突继续保留。确认区显示主体、目标域、管理角色、是否正在处置自己；收到保护/版本冲突时回读并解释，不能自动换成普通角色操作或补建管理员绕过。账号安全、管理员授权和目标域会话处置保留为三个明确入口，避免一个泛化“禁用用户”按钮产生不同作用域。

## 8 新能力的建议契约与待决策

本节列出需要回答的问题和必须保留的安全边界，未冻结公共 API、存储表、迁移版本或排期。实现前各专题须完成威胁模型、失败/并发行为、宿主兼容影响及验收；本文不启动这些实现，也不展开 M1-03/04 已有契约。

### 8.1 管理员强化认证与防滥用

建议先覆盖平台管理员：登录需按策略完成第二因素，危险操作使用绑定主体、当前会话、用途和目标动作的短期再次验证结果。MFA 未完成只能得到受限待验证状态，不能先发完整管理凭证再由前端遮挡。

候选为 TOTP 与 WebAuthn/Passkey，是否先做一种、恢复方式和设备支持需选择。凭证登记须在已验证会话下再次确认；撤销最后因素必须有受控恢复路径。拟定状态包括待登记、已启用、撤销；挑战单次消费、绑定用途并到期，恢复码只展示一次且只存校验材料。管理员重置因素必须审计，不等同禁用MFA后无需再验证。

防滥用需分别限制账号、来源和全局负载，兼顾防枚举、恶意锁他人账号、代理可信来源、分布式计数及失效策略。扫码现有 rate limit 不能当密码入口完整实现。验收需覆盖并发重放、跨会话/动作复用、恢复绕过、因子遗失、管理员撤权以及正常用户恢复。不得复用 device-proof开关假称MFA。

### 8.2 密码恢复与账号中心

建议提供用户自助安全中心与管理员账号处置分离的入口。恢复请求采用一致的外部响应，票据绑定账号/用途/期限，只有校验材料持久化；确认修改与票据消费原子化，重放拒绝。邮件 provider 和可信外部地址由宿主注入，不使用未受信 Host 生成链接。

现有注册邮件是验证码与到期时间，不是密码恢复协议；provider-neutral 邮件契约及宿主注入可复用，恢复票据生命周期另设计。需决定使用验证码或链接，以及MFA丢失是否走另一流程。已有管理员改密全域退役凭证的规则应作为安全基线；自助恢复是否增加撤销范围须明确，不得悄然缩小现有规则。后台不展示明文密码；恢复响应未知必须可安全核对，不能无限发送或多次消费。验收包含账号枚举、过期/并发消费、邮件失败和已停用账号。

### 8.3 邀请、成员加入与离开

建议邀请只授予加入指定tenant的机会，账号复用不自动扩大其他tenant资格。拟定 pending/accepted/revoked/expired 状态，票据绑定目标tenant、被邀请身份和邀请者授权，接受时重检tenant/邀请者/账号当前状态。已经存在有效成员时明确幂等语义，不重建权限。

待定：邮箱验证、现有账号凭证证明、审批与邀请谁优先、邀请过期、初始角色授予及审计。通过邀请登录不得自动获得全局管理权限。成员移除只处理该tenant，不删除共享账号；离职全局处置由有权管理员明确执行。初期不引入通用审批编排引擎。

### 8.4 联合身份、目录同步与服务身份

联合身份以外部 issuer+subject 为稳定身份，不能仅按相同邮箱自动关联高权限账号。需明确定义可信连接、首次登录、显式绑定/解绑、停用传播、claim映射和安全恢复。LDAP读取与SCIM供应属于不同生命周期，不因为支持OIDC就宣称具备。

服务身份需要独立主体类型、允许的token用途/audience、最小业务权限、凭证轮换/吊销、审计主体与人员会话隔离。候选 OAuth client_credentials 必须先定义grant与授权语义，不能把现有client Secret认证当作该grant实现。二者均待需求明确后独立设计，不与当前共享账号规则混合。

### 8.5 审计、可靠事件与可观察性

先盘点每个管理/认证动作的实际事件及缺口，区分安全审计和供产品消费的业务通知。若需要可靠外部事件，建议事务内记录待投递事件、事务外投递，至少一次语义与event ID去重、明确重试/失败隔离、回执和重放授权；不承诺跨系统恰好一次，也不在认证事务内等待远端HTTP。

保留期、脱敏、导出权限、租户边界、投递签名/轮换、事件schema版本、外部目标SSRF限制和审计完整性均需独立契约。新增表/trait需先评估Core与存储职责，不能预先写入tenant_v6。只读查询不得隐式清理历史事件。

### 8.6 密钥轮换、健康与运行保障

需要先区分两条已有能力线：

- **设备证明密钥**：[device-proof lifecycle](../crates/embedded-idp-core/src/access/device_proof/lifecycle.rs) 已有轮换、双签名证明、challenge 消费、expected key/version 冲突与审计，Axum 已有 `/devices/rotate-key`。这是设备持钥者协议，不是管理后台可代用户更换私钥的操作；新模式仅管理也不会因此挂业务设备路由。
- **JWT 签名密钥**：[security/jwt.rs](../crates/embedded-idp-security/src/jwt.rs) 已支持构造时 active key 与 overlap 验证环；[app/bootstrap.rs](../crates/embedded-idp-app/src/bootstrap.rs) 当前传空 overlap，不具备运行时轮换控制面。应复用适配器能力，另定义宿主密钥供应、运行配置、验证窗口、kid稳定性、缓存/传播与退役条件，不能重建签名器或声称当前后台已有轮换按钮。

轮换不以删除旧key强制模拟会话撤销。当前新模式仅管理不发布业务JWKS，未来协议对外映射仍按原工作包处理。

readiness、入口可用性、业务指标和安全审计分别呈现。需定义SQL/锁等待、连接池占用、HTTP总预算与底层取消的真实关系；配置超时不等于任务释放。上线前需另证备份恢复、迁移/回滚、监控告警、Secret供应与管理员应急恢复；部署拓扑和目标SLO本轮不选定。
