## 2 已做内容中哪些需要纠偏

1. **把N2专项逐渐升级为默认产品交付流水线。** 已完成的Mac、Linux容器及H01浏览器补验具有回归和定位价值；但不应由此推导每次PR、任意Core改动和版本tag都必须跑整套H01应用验收。N2是限定环境的工程证据，不是生产就绪认证。
2. **将一个测试环境当成生产制品标准。** Linux arm64、Debian/glibc、release默认features及固定Chromium是本次测试选择。它们不应冻结所有开源使用者的生产架构、基础镜像或浏览器。`scripts/n2-linux/Dockerfile`继续作为测试工具，不作为生产Dockerfile交付承诺。
3. **发布tag绑定过重。** `release/x.y.z`可以是本仓库版本质量检查入口，但不能自动等同于“生产单体全量验收/发版/部署”。也不应为了这个tag提前设计生产配置、镜像仓库、环境审批或下游CD。
4. **提速优先级受到专项耗时误导。** 普通CI最近样本约3.5–5.5分钟；最终N2为18分34秒，其中构建4分58秒、八套功能及各套准备/清理12分43秒。继续为手动专项引入复杂缓存、64组通用保底、自动选套协议、可复用编排和分片，维护成本可能高于日常收益。应先避免把专项变成默认必跑，再谈缓存。
5. **证据归档方式不适合常态化照搬。** 本次首次验收和缺陷定位所保留的七次原始公开ZIP、日志与复审记录继续保全；日常开源CI不必每次都把全部附件写入Git。常规日志/artifact保存在Actions，版本保留摘要、SHA、用例范围和附件索引，重要缺陷另留最小复现。证据完整性与秘密保护仍保留。

尚未出现生产部署越界：仓库目前只有[普通CI](../.github/workflows/ci.yml)和手动N2 workflow（历史源码：`git show a3fcd72:.github/workflows/n2-functional.yml`），没有部署/镜像推送/生产环境操作。本轮纠正的是职责和后续门槛扩张，不把已经完成的专项测试或必要修复判为无效。此前工具解析、异步等待、按钮名称和结果收尾修复仍有价值。

## 3 推荐的最小CI分层与按范围规则

### 日常CI：上游质量基线

保留现有Rust格式/构建/工作区测试、开发HTTP feature与release安全专项、设备/扫码向量、Web测试/构建/bundle及示例消费者构建。不同feature、profile、消费者的覆盖面不同，目前不能据“命令相似”删除。先保持这条已知约数分钟的基线，不立即改造成复杂的路径调度框架。

后续若新增或调整公开契约、存储、路由、初始化/迁移工具，应验证相应模块及适配器；必要时使用临时PG。**适配器的真实数据库回归属于上游质量，不属于生产部署验收**，不能因为CD在下游就省掉。是否接入自动CI及其具体用例，在恢复工作时按实际变更确定，本轮不扩大既有普通CI。

### 参考应用/浏览器专项：按需要选择

| 变更范围 | 推荐验证层次 |
| --- | --- |
| 仅说明文档/历史证据 | 静态一致性与链接；不新增N2运行 |
| Core/密码学/会话/授权/设备协议 | 相应单元、契约、安全、适配器/路由回归；影响参考装配时再选专项 |
| HTTP/Postgres适配器、初始化/迁移工具 | 相应真实隔离集成和错误路径；不直接升级为所有H01 UI流程必跑 |
| Web客户端或公共会话/作用域代码 | Web测试＋相关浏览器身份/会话/越界/未知结果恢复；影响面不明时再用完整N2定位 |
| 客户端页面 | 对应clients功能与涉及的恢复/标识兼容用例 |
| 权限/角色页面或可复用权限组件 | authorization及相关console/N1用例 |
| 设备/会话/管理员/审计页面 | security及涉及的console用例 |
| 参考应用配置、资源挂载、启动和重建 | 对应gates、会话及必要UI装配检查 |
| 测试驱动/收尾/证据工具 | 工具离线回归，必要时专项真实验证；不把每次工具测试修改默认变成全应用验收 |
| 版本集成复核、跨模块复杂缺陷或维护者明确要求 | 可手动运行完整N2，维持当前严格八套门槛 |

上述是**验证范围建议，不是已经实现的自动选择器**。不能只凭目录名跳过跨模块风险；公共身份/安全改动需追踪真实受影响路径，无法确定时升级相应集成验证或手动全量。

当前CI driver的finalize/verify固定要求八套，不能简单删suite后声称局部通过。首版推荐保留当前手动全量入口；确有持续需求才另设计受校验的局部入口。局部结果必须独立命名并记录选择理由和未执行范围，不能冒充264组全量通过。无需现在为所有局部修改强制追加固定64组，也不在本轮搭建自动分类/汇总框架。

## 4 构建缓存：收敛后的优先级与规则

恢复CI维护后，先评估普通CI的依赖下载缓存，推荐仅缓存pnpm store、Cargo registry/index/src和git依赖缓存，不先缓存`node_modules`、`target`、`dist`或最终制品。每次仍执行frozen/locked安装、实际检查/测试和构建；缓存命中不等于测试已跑。

pnpm key至少包含OS/架构、实际Node/pnpm版本、相关lockfile/配置哈希；Cargo key至少包含OS/target、Rust版本、Cargo.lock和相关Cargo配置。优先精确匹配，跨平台/工具链不恢复；错配、缺失或服务异常退回普通下载。只缓存可公开的依赖材料，排除cargo凭证、env、keys、PG数据、profile和结果日志。

缓存保存只来自成功的可信main运行；PR（包括fork）不保存，首版推荐禁用其缓存恢复；tag和手动运行只读可信缓存。新增Actions在恢复实施时核对支持能力并固定完整SHA，保持最小权限。使用独立精确路径、有界操作和容量预算；仅缓存服务异常允许性能降级，测试/构建/来源/安全错误仍失败。缓存可被有读取能力的PR访问、不能存秘密，依据见[GitHub缓存规则](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)。

N2 Docker层缓存降为低优先级，可先不实施。若以后专项运行足够频繁，再评估依赖层先复制、BuildKit local导入/导出和可信缓存；不为它现在引入registry、常驻builder或修改daemon。默认docker driver能否导出缓存需要containerd image store等实际能力核对，不支持则保持冷构建，依据：[Docker缓存后端](https://docs.docker.com/build/cache/backends/)、[local缓存](https://docs.docker.com/build/cache/backends/local/)、[层顺序](https://docs.docker.com/build/cache/optimize/)。

现有prepare从构建日志检查Node/Rust版本；若将来引入层缓存，必须改用本次实际版本探测/来源检查等可靠证据，不能删除版本门槛或填入推荐值。被冻结复用的测试层标记cached；本次要求的功能验证仍实际执行。缓存收益必须包含恢复/保存时间，测不到净收益就停用，不承诺固定提速比例。

## 5 release/x.y.z：上游版本全量质量检查，不承担CD

未来推荐触发关系如下；**本轮不修改任何触发器**：

| 事件 | 开源仓库质量检查 | N2 / 部署 |
| --- | --- | --- |
| pull_request、push main | 保留普通CI；必要模块专项随实际影响安排 | 不自动要求八套N2；无部署 |
| workflow_dispatch | 维护者明确指定的专项；保留现有N2全量入口 | 只证明所选范围；无部署 |
| 新建release/x.y.z tag | 对该tag解析的commit运行上游版本全量质量检查 | 不默认绑定H01八套；无生产验收、部署或包/镜像推送 |
| 普通开发分支push、schedule、release published | 不新增触发 | 不新增触发 |

这里的“版本全量”指届时定义的**模块/适配器/API与UI契约、编译及打包质量检查全集**，不是生产单体全量。沿用普通CI全部既有安全专项；发生存储/HTTP/宿主契约调整时补齐相应集成测试，不能把关键安全失败降级。若版本包含重要参考UI/装配变更，可另由维护者选择完整N2；N2结果继续限定H01及所测组合。

后续可用`release/**`进入tag校验，严格接受`^release/(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`，如`release/3.0.0`。删除不执行；非法/强制改写tag停止验收并报错；记录tag对象、解析commit、run/attempt与实际checkout SHA。推荐版本来自main可达提交，维护分支另定；版本与实际发布包策略核对，不预先强制所有独立包/Web/宿主同步版本。失败修复用新commit/新版本，不能挪动旧tag掩盖失败。

现有普通CI使用`v*` tag，N2仅手动；恢复实施时再决定将上游版本入口统一为`release/**`并停止新的`v*`触发，历史tag不动。tag的path筛选不能代替显式版本质量门槛，依据见[GitHub触发语法](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)。不在本轮建立可复用流水线、发布环境审批、生产Secret或跨仓库调用。

下游仓库自行选定本仓库tag/commit/包，组装自己的配置和业务集成，构建生产镜像，验证部署环境及业务端到端，再执行自己的发布/迁移/回滚。下游的release tag、部署授权和证据与上游各自独立；本仓库tag通过不能代签下游。

## 6 保留的安全、清理和证据门槛

认证授权、管理/业务用途、租户/业务隔离、会话刷新/退出/重放、配置拒绝及写后恢复等合同仍由相应上游测试覆盖。所需测试一旦选定，不忽略失败退出码，不强制点击绕开错误，不伪造结果，不把未执行当passed。

只有实际启动临时服务/容器/PG/浏览器的专项才承担对应资源收尾；保持独立凭证/schema、私有目录、run/attempt所有权、进程/profile关闭、容器/卷/网络回读及失败安全处理，不全局prune。清理未知或不完整不能转绿。普通单元测试无需承担生产备份恢复和上线运行手册。

常规CI保留SHA/工具版本、范围、结果、错误和artifact索引；集成专项沿用脱敏白名单、精确文件集合/哈希和有界always收尾/上传。无秘密进入日志、缓存或Git。需要正式签收的专项继续核对下载ZIP、publication和实际保留期限；不宣称Actions日志永久存在。

本次N2七次运行已按原授权完整保全，原始附件和历史失败不改写。以后不默认复制同等体量证据进Git；保留必要摘要/复现/索引，完整附件使用Actions或届时选定的归档位置。任何生产DB操作/共享环境验证均不属于本方案。
